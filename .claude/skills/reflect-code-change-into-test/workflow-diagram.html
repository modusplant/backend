Skill workflow

reflect-code-change-into-test

Creates, modifies, and deletes tests for every domain and infrastructure area touched by unpushed changes, batched per area.

Skill file: .claude/skills/reflect-code-change-into-test/SKILL.md. That file is the source of truth; this page is a human-oriented view of it.

Step, in run order Document read File written Terminate or skip Branch or fallback Repeated per item
  1. 1

    Resolve Target Classes

    Collect every .java class not yet pushed: uncommitted changes (git status --porcelain) combined with committed-but-unpushed ones (git diff against the upstream, or origin/main if none).

    The combined list is empty.
  2. 2

    Resolve Target Areas

    Match each class path against domains/<area>/ or infrastructure/<area>/. Group the matches into one bucket per (area, kind), where kind is domain or infra.

    Read.claude/CLAUDE.mdArea names and the account sub-domain path mapping (e.g. normal-identity → domains/account/normal/).
    Classes matching neither pattern are dropped and reported as unmatched.
    Every class was dropped as unmatched.
  3. ↻ Steps 3–6 repeat for each area bucket
    1. 3

      Load the Area Feature

      Load the area's test settings: ErrorCode class, path exceptions, TestUtils paths, and so on.

      Fallback order
      1. Use the feature file if it exists.
      2. Otherwise, derive the same facts from the area's rule file plus the actual src/main / src/test layout.
      3. If neither file exists, skip this bucket and continue with the next one.
      Read ①.claude/documents/test-<kind>-<area>-feature.mdPer-area test feature: the preferred source.
      Read ②.claude/rules/<kind>-<area>-details.mdPer-area convention rules: the fallback source.
      Neither file exists. The area and its classes are reported, and the user is asked to create the rule file first.
    2. 4

      Apply Excluded Classes

      Never generate tests for enum classes, exception classes, constructor-only classes, or anything listed under the feature's Excluded-classes additions.

    3. 5

      Apply the Test Architecture & Strategy

      Start from the Pure Unit Test baseline, then apply the area-specific adjustments from the feature: ErrorCode assertions, path exceptions that may use a real Spring context or DB, and the servlet mock pattern.

      Read.claude/rules/test-architecture-details.mdProject-wide test baseline, inlined into the skill at load time.
      jOOQ repository test policy (for framework/outbound/jooq/repository, if the feature names one)
      • excluded: generate no test.
      • integration-test: @SpringBootTest with a real DSLContext and seeded data.
      • unit-test (jOOQ MockConnection/MockDataProvider): no Spring context, and no Mockito-mocked DSLContext.
    4. 6

      Write tests using the TestUtils convention

      Reuse constants from the area's common/constant path and from the feature's shared constant paths, creating any that are missing. Place helpers per the feature's Group A (fields) and Group B (methods) target paths.

      Writesrc/test/java/kr/modusplant/…Test classes created, modified, or deleted for this bucket.
  4. 7

    Report the Summary

    For each processed area: the classes whose tests were created, modified, or deleted. It also lists skipped areas with their unprocessed classes, and the unmatched classes dropped in step 2.

Guardrails

  • Runs only when invoked by .claude/skills/postprocess-main-code-change/SKILL.md, never on its own initiative.
  • Edits under src/main/** are disallowed.
